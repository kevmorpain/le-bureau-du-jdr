# Journal de décisions (ADR)

Décisions d'architecture du chantier D&D 5.5 et du nettoyage du socle. Format court :
**Contexte → Décision → Pourquoi**. Les détails techniques vivent dans
[`rules-engine.md`](./rules-engine.md) ; les constats dans [`architecture-audit.md`](./architecture-audit.md).

---

### <a id="d1"></a>D1 — Cohabitation 5 / 5.5, pas remplacement
- **Contexte** : l'app ne gère que la 2014 ; on veut ajouter la 2024.
- **Décision** : les deux systèmes cohabitent ; le ruleset est **figé par personnage** à la création.
- **Pourquoi** : les fiches existantes restent intactes et jouables ; les deux systèmes ne sont pas compatibles poste à poste.

### <a id="d2"></a>D2 — Valeur du ruleset = `'5'` / `'5.5'`
- **Décision** : discriminant `ruleset` (`'5'` | `'5.5'`) sur `character_sheets`, `character_species`, `classes`, `backgrounds`. Millésimes 2014/2024 = repères de lecture seulement.
- **Pourquoi** : noms quasi officiels ; permet à deux entités homonymes (Elfe 5 vs 5.5) de coexister sans matching de nom fragile.
- **Séquencement** : le flag distingue les éditions = **enablement**, pas fondation → posé en **Phase 2**, *après* la phase de clean (cf. roadmap `dnd-5.5.md`). Un prototype de migration a été retiré pour repartir propre.

### <a id="d3"></a>D3 — Classe & historique deviennent dérivables comme l'espèce
- **Contexte** : l'espèce dérive tout via `features`+`effects` ; classe & historique figent leurs grants à la création depuis le front.
- **Décision** : aligner classe & historique sur le pattern espèce. **Grants → effects** ; **identité fixe → colonnes** ; **choix → `progression`** (D4).
- **Pourquoi** : rejette l'idée initiale de colonnes plates (`saving_throws`, `ability_bonuses`) qui **dupliqueraient** ce que les effects font déjà pour l'espèce. On généralise un pattern éprouvé, pas un compromis.

### <a id="d4"></a>D4 — Modèle de choix `progression` + `character_choices`, owner = `featureId`
- **Contexte** : la « référence » des choix (quoi/quand/parmi quoi) est front-only et dupliquée builder↔level-up ; la config est éparpillée (subclassId, pactBoon, ASI, choices JSON).
- **Décision** : table `progression` (référence) liée à une **`feature`** + table `character_choices` (config). Owner = `featureId` (pas d'owner polymorphe).
- **Pourquoi** : la feature porte déjà niveau/owner/ruleset ; « la table de références = quoi/quand » **est** `features`. Une seule source, builder & level-up la lisent.

### <a id="d5"></a>D5 — Valeurs typées / FK, pas de texte libre
- **Décision** : unions typées pour les ensembles fermés (`kind`, `pact_boon`…) ; **FK** partout où une table existe (`selectedSubclassId`, `selectedFeatureId`, `selectedSpellId`, `selectedAbilityId`) ; strings typées seulement pour ce qui n'a pas de table (compétences/langues/outils).
- **Pourquoi** : intégrité + pas de magic strings ; cohérent avec `ability_scores` déjà en table+FK.

### <a id="d6"></a>D6 — Couche `shared/rules/` : const canonique par ensemble fermé
- **Contexte** : chaque ensemble fermé est défini 3–5× (union + enum + table + Zod recopié) → dérive déjà constatée (casse des compétences).
- **Décision** : **une const canonique** par ensemble dans `shared/rules/` ; type, Zod, table et i18n en **dérivent**.
- **Pourquoi** : source unique de vérité ; **dissout le débat table-vs-union** (la table devient une projection seedée). Héberge aussi le moteur de règles (slots, PV).

### <a id="d7"></a>D7 — Table `skills` maintenant (langues/outils plus tard)
> **Remplacée par [D27](#d27)** : la table `skills` est supprimée (migration 0153) ; la constante `SKILLS` et la validation Zod aux écritures portent la casse canonique.
- **Décision** : créer une table `skills` dès la Phase 1 ; différer `languages`/`tools`.
- **Pourquoi** : cohérence avec `ability_scores` (déjà en table), intégrité FK, et ça **force** la casse canonique → répare le bug `sleightOfHand`/`sleight_of_hand`. Langues/outils = ensembles plus ouverts, non bloquants.

### <a id="d8"></a>D8 — Résolution des choix : dériver live, pas matérialiser
- **Décision** : un choix résolu n'est pas matérialisé en `character_features` ; la fiche dérive les features/effets actifs en joignant `character_choices → features` + gating niveau. On ne matérialise que l'état runtime (`currentUses`).
- **Pourquoi** : cohérent avec l'intention « dériver un max » (l'espèce le fait déjà) ; moins de données figées à re-synchroniser.

### <a id="d9"></a>D9 — Retrofit 5.5-first
- **Décision** : les fondations transverses (`shared/rules/`, casse, union `Effect`, transactions, DRY API) touchent le 2014 sous tests d'équivalence. Les virages de comportement (grants de classe → effects, backgrounds → features) sont construits **pour le 5.5 d'abord** ; le 2014 est retrofité plus tard.
- **Pourquoi** : migration **additive** = zéro régression ; on prouve le modèle sur le 5.5 avant de migrer l'existant.

### <a id="d10"></a>D10 — Résolution = fonction pure partagée
- **Décision** : séparer **catalogue** (statique, cachable au edge par ruleset) et **projection perso** (dynamique). `resolve(character, catalog)` est une **fonction pure dans `shared/rules/`**, lancée par le serveur (autorité) *et* le client (UX).
- **Pourquoi** : une logique, deux appelants, zéro duplication. Le cache découle du fait que le catalogue est pur.

### <a id="d11"></a>D11 — Labels via i18n, structure en const
- **Décision** : les consts `shared/rules/` portent la structure (clés machine + relationnel) ; les labels vivent dans l'i18n (`@nuxtjs/i18n`, `fr.json`). Erreurs via `nuxt-zod-i18n` (déjà installé).
- **Pourquoi** : const = structure, i18n = présentation ; cohérent avec l'investissement i18n existant ; prêt pour l'EN.

### <a id="d12"></a>D12 — Tests par contrat, pas snapshots aveugles
- **Décision** : assertions sur des **valeurs D&D vérifiées à la main** (fixtures : Ambroise + 1 martial + 1 caster), d'abord sur les sous-composables purs puis sur les fonctions extraites en `shared/rules/`.
- **Pourquoi** : un snapshot brut fige les bugs pré-existants et casse au moindre changement de forme ; le contrat révèle les bugs et devient le moteur du refactor.

### <a id="d13"></a>D13 — Migration additive
- **Décision** : construire le modèle propre pour le neuf ; les persos 2014 gardent leurs snapshots (redondants, inoffensifs) ; migration big-bang du 2014 plus tard, une fois l'équivalence prouvée.
- **Pourquoi** : zéro régression, transition douce.

### <a id="d14"></a>D14 — API : atomicité + autorité de dérivation
- **Décision** : `db.batch()` (atomique D1) sur les écritures multiples ; le serveur **dérive et valide** au lieu de faire confiance aux valeurs calculées par le client.
- **Pourquoi** : un insert échoué ne doit pas laisser un personnage à moitié créé ; anti-triche + robustesse. Détails : `rules-engine.md` §API.

### <a id="d15"></a>D15 — Matérialisation = grants passifs seulement ; une option se reconnaît à son `tag`
- **Contexte** : la classe est encore **matérialisée** (features copiées dans `character_features` à la création/au level-up) — la [D8](#d8) veut à terme la *dériver live* comme l'espèce, mais c'est le point 6 de la roadmap. Or le lot 4c introduit des features-**options** (les 3 faveurs de pacte, puis métamagie/manœuvres/styles) en `class_feature`/`subclass_feature` : les sweeps de matérialisation existants (`WHERE class_id … AND feature_type = 'class_feature' AND level ≤ …`) les attribueraient **toutes** d'office.
- **Décision** : les sweeps ne matérialisent que les **grants passifs** ; une feature qui est une **option d'un groupe de choix** se reconnaît à son **`tag` non nul** (la sémantique posée en [4b](#d6)/`shared/rules/featureTags.ts` : « un tag marque une feature qui est une option »). Prédicat nommé `isPassiveGrant()` (`server/utils/features.ts`) = `isNull(features.tag)`, appliqué aux quatre sweeps (create + level-up, classe + sous-classe). Une option n'est obtenue que si elle est **choisie** (`progression` + `character_choices`) puis dérivée live.
- **Pourquoi** : ce n'est pas une rustine mais l'application directe du concept que `tag` encode — et ça **généralise** à tous les groupes futurs sans code supplémentaire. Les alternatives (détacher l'option de sa classe via `class_id = NULL`, ou un `feature_type` dédié par groupe) exploitent un effet de bord et cassent l'appartenance / regonflent l'union de types. **No-op prouvable** aujourd'hui (aucune `class_feature`/`subclass_feature` n'est taguée ; les invocations sont hors sweeps par leur `feature_type`). **Jalon provisoire** : disparaît quand la classe cessera d'être matérialisée (point 6).

### <a id="d16"></a>D16 — Sourcing du contenu 5.5 : aidedd + validation par lots (option A)
- **Contexte** : le contenu 5.5 (espèces, historiques, classes, dons, maîtrise d'armes) doit être seedé avec une **exactitude élevée** (une valeur fausse = fiche fausse) ; `WebFetch` fonctionne sur aidedd (cf. `dnd-5.5.md` §4) mais passe par un petit modèle d'extraction qui **bruite**.
- **Décision** : **source = aidedd** — c'est la traduction FR **officielle** du PHB 2014 **et** 2024, donc la page FR fait autorité pour les libellés. **Méthode = option A** : pour chaque volet, fetch des pages de **détail** → présentation d'une **table validée par l'auteur** → seed. L'EN (`/feat/<slug>`, `/en/<class>-2024/`) sert au mapping libellé FR → clé machine EN ([D11](#d11)) et de contrôle anti-bruit.
- **Pourquoi** : garde la vitesse du fetch tout en plaçant l'**autorité d'exactitude sur l'auteur**, volet par volet, et attrape le bruit d'extraction **avant** le seed. Cohérent avec le contenu 2014, déjà issu d'aidedd. Deux règles dures (page de détail uniquement ; recouper chaque entrée) : `dnd-5.5.md` §4.

### <a id="d17"></a>D17 — Espèce = base + lignée, sous-entité symétrique de la sous-classe (unifié 2014/2024)
- **Contexte** : le 2014 modélise les variantes d'espèce comme des **espèces séparées** (Haut-elfe, Nain des montagnes…), et le regroupement « base → variante » n'existe QUE dans le front hardcodé (`app/data/character-builder.ts`, champ `subraces[]`, base virtuelle `dbName:null`). La 2024 rebaptise « race » en **origine** et présente « espèce de base + **lignée** choisie » avec des bénéfices **étagés** par niveau (Drow : sorts niv.1/3/5). Les deux structures sont le même concept.
- **Décision** : first-classer ce concept dans les **données**, calqué sur `classes → subclasses`. Nouvelle table **`species_lineages`** (FK `species_id`, parent-gated, sans `ruleset` comme `subclasses`) ; **`features.lineage_id`** + `feature_type='lineage_feature'` (features de la lignée, gated par `level_required`) ; choix via **`progression` + `character_choices.selected_lineage_id`**. La base (`character_species`) porte les traits communs (`species_features`) ; les bonus de carac. 2014 d'une variante = `ability_increase` sur ses features ; les bénéfices étagés = `spell_grant`/`unlockLevel` (déjà utilisés par le Tieffelin 2014). **Unifié pour les deux éditions** : le 2014 est **retrofité** (pas laissé en espèces séparées), coût de migration des fiches vivantes **assumé** (choix utilisateur « le plus propre et modulaire »).
- **Pourquoi** : un seul mécanisme couvre sous-race 2014 et lignée 2024, réutilise la machinerie de choix éprouvée (`progression`, lot 4c) et **vide** le blob front (roadmap : builder dérive du catalogue). Alternatives écartées : (a) « pareil que 2014 » = espèces séparées + regroupement hardcodé → alimente la dette qu'on supprime ; (b) colonne `parent_id` (B1) → unifie mais garde les variantes comme espèces séparées, moins fidèle à la 2024. La restructuration du 2014 se fait **additive + sous tests d'équivalence** ([D9](#d9)/[D12](#d12)/[D13](#d13)) : lots séparés (schéma → résolution → pilote Elfe + équivalence → migration des fiches → builder → rollout). Détails : `dnd-5.5.md` §3.

### <a id="d18"></a>D18 — Préférences : portées par la fiche, avec des défauts de compte hérités
- **Contexte** : l'app n'a **aucune couche de préférences** (ni table, ni colonne, ni composable ; `useStorage` ne porte que de l'état de jeu). Le besoin apparaît dès qu'on veut laisser le joueur reprendre la main — désactiver les jets de dés, saisir un résultat lui-même, surcharger une valeur dérivée (cf. [`fonctionnalites-manquantes.md`](./fonctionnalites-manquantes.md#n--contrôle-manuel--préférences), famille N). ⚠️ Décision **hors chantier 5.5** : elle ne touche ni les règles ni le ruleset, mais elle contraint le schéma, d'où sa place ici.
- **Décision** : la préférence vit **sur `character_sheets`** ; `users` porte des **défauts** qui s'appliquent aux fiches n'ayant pas tranché. Résolution par **héritage live** — `fiche ?? compte ?? défaut codé` — et **non** par copie à la création. Conséquences directes :
  - colonne **nullable, SANS `DEFAULT`** : `NULL` signifie « hérite », qui n'est **pas** « désactivé ». Chaque réglage est donc **tri-état** (`oui` / `non` / `hérité`) côté schéma *et* côté UI (un `UCheckbox` binaire ne suffit pas) ;
  - stockage en **colonne JSON typée** `$type<Preferences>()` des deux côtés, avec un ensemble canonique unique dans `shared/` dont le type et le Zod **dérivent** ([D6](#d6)) — un nouveau réglage n'est alors pas une migration ;
  - résolution = **fonction pure partagée** serveur + client ([D10](#d10)), exposée **déjà résolue** par le GET fiche pour que le client ne ré-implémente pas la fusion. Le GET sélectionne déjà l'owner réduit à `{id, name}` : l'élargir à `{id, name, preferences}` est une ligne.
- **Pourquoi** :
  - **l'héritage plutôt que la copie** applique [D8](#d8) (« dériver, pas matérialiser ») : changer un défaut de compte se propage à toutes les fiches qui n'ont rien tranché, ce qui *est* le sens de « défaut ». Une copie à la création figerait un instantané et surprendrait — régler un défaut après coup ne changerait rien ;
  - **zéro backfill** : les fiches existantes restent à `NULL`, donc héritent, donc sont correctes sans migration de données ([D13](#d13)) ;
  - **la fiche comme porteuse** colle à l'usage : un personnage joué en théâtre de l'esprit et un autre sur grille n'ont pas les mêmes réglages, alors que le compte capture la préférence durable du joueur.
- **Écarté** : *tout sur `users`* (ne permet pas de varier par personnage) ; *tout en `localStorage`* (ne suit pas le joueur d'un appareil à l'autre, alors que l'app est une PWA installable) ; *une colonne typée par réglage* (une migration par préférence, pour un ensemble voué à grandir).

### <a id="d19"></a>D19 — PV max dérivés : la fiche ne stocke que la part « dés »
- **Contexte** : `character_sheets.max_hp` était une **somme stockée** dont chaque terme incluait le modificateur de CON *du moment*. Un +2 CON à un palier d'ASI (mod +2 → +3 au niveau 8) n'ajoutait aucun PV, alors qu'AideDD (« Au-delà du niveau 1 ») le veut : quand le modificateur de CON augmente de 1, le maximum augmente de 1 **par niveau atteint**. Seul Robuste était rétroactif, recalculé à l'affichage. Et le serveur, qui remet les PV au repos, ne connaissait pas le maximum effectif (Robuste, moitié à l'épuisement 4) : il restaurait la somme stockée (B16, #203).
- **Décision** : `max_hp` devient **`hp_base`** (migration 0117) : la part des dés lancés ou des valeurs fixes, **hors CON et hors bonus par niveau**. Le maximum se calcule à la lecture, par une fonction pure partagée (`shared/rules/hitPoints.ts`) : `hp_base + (mod CON + bonus `hp_per_level`) × niveau total`, divisé par deux (arrondi inférieur) à partir de l'épuisement 4, plancher à 1. Pour que le **serveur** connaisse la CON, le calcul des caractéristiques sort des composables du navigateur : `shared/rules/abilityScores.ts` (`computeAbilityScores`) et `shared/rules/characterEffects.ts` (effets d'espèce, de capacités, d'ASI ; objets équipés et liés ; effets temporaires), alimentés côté serveur par `server/utils/characterSheetLoader.ts` — le chargement du GET, désormais partagé avec le repos, le level-up et la création.
- **Conséquences** :
  - le **minimum de 1 PV par niveau** (« minimum 1 », AideDD) se joue **au gain** : `hitPointGain(dé, mod CON naturel)` relève la part stockée de ce qui manque ; le mod naturel exclut objets et effets temporaires, qui ne rendent pas un gain permanent ;
  - le level-up n'envoie plus que le **dé** (`hpDie`), le serveur le borne par le dé de la classe (borne haute qui manquait, #124) ; la création envoie `hpBase`, borné à `[niveau, niveau × dé]` ;
  - `hp_per_level` compte pour l'espèce et les objets, plus seulement les dons (l'éditeur d'objet le proposait, rien ne le lisait) ;
  - un objet équipé qui change la CON (Amulette de santé) ou un effet temporaire actif déplace le maximum, comme la règle l'exige ; l'« Édition directe » saisit le total affiché et stocke ce qui reste.
- **Migration des fiches existantes** : `hp_base = max_hp − mod CON actuel × niveau total`, sans reconstituer l'historique (les fiches qui avaient gagné de la CON en route avaient été corrigées à la main). Le score de CON actuel reprend en SQL les sources de `computeAbilityScores` ; `test/nuxt/hpBaseMigration.test.ts` vérifie, sur chaque source, que le maximum dérivé après migration égale celui d'avant.
- **Pourquoi** : applique [D8](#d8) (dériver, pas matérialiser) et [D10](#d10) (une règle pure partagée serveur + client) ; couvre d'un coup ASI, dons, objets, builder et level-up, là où une correction « au level-up seulement » aurait laissé les objets et l'édition des scores. **Écarté** : (b) ajouter Δmod × niveaux au level-up — ne couvre ni objets ni édition manuelle des scores.
- **Limites assumées** : la règle « un seul repos long par période de 24 h » (AideDD) n'est pas portée — l'app n'a pas d'horloge de jeu ; « Ténacité naine » du Nain des collines (+1 PV par niveau) n'émet toujours aucun effet `hp_per_level` (contenu, hors lot).

### <a id="d20"></a>D20 — Ressources de classe : le compteur existant, enrichi, plutôt qu'un « pool »
- **Contexte** : ki, points de sorcellerie, rages, Inspiration bardique… n'avaient aucune mécanique ([#142](https://github.com/kevmorpain/le-bureau-du-jdr/issues/142)–[#147](https://github.com/kevmorpain/le-bureau-du-jdr/issues/147)). Le registre y voyait « un concept de pool de ressource à concevoir une fois », car `currentUses` « compte des usages unitaires ».
- **Décision** : pas de table ni de concept neuf. `maxUsesFormula` + `rechargeType` + `currentUses` (dépensé) suffisent : le ki *est* un compteur dépensé par paquets. On y ajoute (1) les formules seedées, (2) des formules évaluées au **niveau de la classe propriétaire** (le contexte lisait toujours la classe principale), (3) `meta` (clé de réserve, `pool`, `whileActive`, `spends`, `cost`…), (4) un état `character_features.active`, (5) des effets typés à `Formula` dérivés par des fonctions pures partagées (`shared/rules/classResources.ts`).
- **Pourquoi** : une table d'état supplémentaire aurait dupliqué le compteur, sa remise à zéro au repos et son endpoint. Aucune règle par classe dans le code : tout est de la donnée seedée ([North Star](./consolidation-2014.md)), migrée par la 0120 sans reseed.
- **Conséquences** : le repos lit une seule règle côté serveur et client (`restRecovery`) ; un effet `resource_regain` exprime Source d'inspiration et la restauration du niveau 20 de l'ensorceleur ; les emplacements créés par la sorcellerie sont une colonne `created` (0121) remise à zéro au repos long ; la Rage suspendue en armure lourde l'est par donnée (`suspendedByHeavyArmor`).
- **Limites assumées** : Attaque supplémentaire ne se cumule pas (maximum), mais l'attaque de l'arme de pacte (Lame assoiffée) n'est pas comptée ; les sous-classes qui dépensent ki ou points restent en texte ; la Forme sauvage n'enregistre pas les PV de la bête ; la Rage ne s'arrête pas d'elle-même (inconscience, tour sans attaque) — seul un repos ou le bouton y met fin (corrigé par [D33](#d33)).

### <a id="d21"></a>D21 — CA sans armure et vitesse : deux effets nommés, `walking_speed` reste la vitesse de base
- **Contexte** : la CA d'un Barbare ou d'un Moine sans armure, le Déplacement rapide / sans armure et la Force requise des armures lourdes n'étaient pas calculés ([#141](https://github.com/kevmorpain/le-bureau-du-jdr/issues/141), [#148](https://github.com/kevmorpain/le-bureau-du-jdr/issues/148), [#157](https://github.com/kevmorpain/le-bureau-du-jdr/issues/157), [#160](https://github.com/kevmorpain/le-bureau-du-jdr/issues/160), [#136](https://github.com/kevmorpain/le-bureau-du-jdr/issues/136)). `walking_speed` avait deux sens : valeur **absolue** pour les traits d'espèce et de lignée (9, 10,5…), **bonus** pour le don Mobile et l'éditeur d'objets — et aucun lecteur côté fiche, si bien que Mobile ne donnait rien.
- **Décision** : `unarmored_defense` (base + caractéristiques, bouclier permis ou non) et `speed_bonus` (`Formula` + condition d'armure) sont des effets seedés ; le calcul est dans des fonctions pures (`shared/rules/armorClass.ts`, `shared/rules/speed.ts`). `walking_speed` ne désigne plus que la vitesse de base. La pénalité de 3 m de l'armure lourde suit la colonne Force d'AideDD (`strength_requirement`), pas le type d'armure ; l'effet `equipment_penalty` du Nain la neutralise. La migration 0123 requalifie les `walking_speed` d'un don ou d'un objet en `speed_bonus`, sans reseed.
- **Pourquoi** : additionner tous les `walking_speed` aurait doublé la vitesse des espèces ; une règle par classe (`if Barbare`) contredit le [North Star](./consolidation-2014.md). **Écarté** : lire `walking_speed` comme un bonus partout, et renommer la vitesse de base (la lignée et le catalogue la lisent comme absolue).
- **Limites assumées** : la CA sans armure retient la meilleure source (AideDD : on n'en cumule pas), même quand `10 + DEX` est meilleure ; le bouclier ne suspend pas la Résistance draconique (le texte dit « sans armure », là où le Barbare et le Moine citent le bouclier à part — lecture, pas citation) ; les bonus de vitesse ne s'appliquent pas au vol, à la nage, à l'escalade ni au creusement ; le récapitulatif du builder affiche encore la vitesse d'espèce seule.

### <a id="d22"></a>D22 — Moteur de jets : la fiche calcule la politique d'un jet, le lanceur l'applique
- **Contexte** : `roll()` jetait un d20 nu. La fiche *affichait* pourtant les désavantages (états, épuisement, armure, arme lourde), l'effet `reroll` du Halfelin et l'effet `advantage` étaient seedés, le critique ne colorait qu'un toast, et Touche-à-tout, Savoir-faire, Critique brutal ou le critique du Champion ne faisaient rien ([#108](https://github.com/kevmorpain/le-bureau-du-jdr/issues/108), [#132](https://github.com/kevmorpain/le-bureau-du-jdr/issues/132), [#140](https://github.com/kevmorpain/le-bureau-du-jdr/issues/140), [#149](https://github.com/kevmorpain/le-bureau-du-jdr/issues/149), [#150](https://github.com/kevmorpain/le-bureau-du-jdr/issues/150), [#182](https://github.com/kevmorpain/le-bureau-du-jdr/issues/182), [#183](https://github.com/kevmorpain/le-bureau-du-jdr/issues/183)).
- **Décision** : les règles sont pures et partagées (`shared/rules/rolls.ts`) : résolution du mode (annulation avantage / désavantage), tirage du d20 (relance, plancher, plage de critique), doublement des dés. Chaque jet de d20 de la fiche porte un type (`D20Kind`) ; `useCharacterRolls` en tire une `D20Policy` depuis les états, l'armure et les effets, et la page la fournit à `useDiceRoller` (`provide` / `inject`). Les sites d'appel ne portent que le type du jet, jamais une règle. Cinq effets nommés (`half_proficiency`, `proficient_check_minimum`, `critical_range`, `critical_extra_dice`, `halve_damage_reaction`) et `advantage` étendu (`attack`, `initiative`) sont seedés ; la migration 0124 les pose sur les bases déjà peuplées, sans reseed. Une seconde passe (migration 0125) rend les conditions interprétables **quand la fiche les connaît** : `advantage.unless` (états qui le suspendent : Sens du danger sans aveuglé, assourdi ni incapable d'agir), `advantage.scope: 'strength_melee'` (Attaque téméraire), `weapon_damage_dice.needsAdvantage` (le mode du dernier jet d'attaque dit si l'Attaque sournoise est permise, refusée ou à confirmer) et `spell_damage_bonus`. Attaque téméraire est une capacité qui s'active comme la Rage (`meta.whileActive`) et prend fin au « Nouveau tour » (`meta.endsOnNewTurn`). L'historique et l'initiative sont de l'état de rencontre : `useStorage` par fiche, comme les conditions.
- **Pourquoi** : la logique dans chacun des ~15 sites d'appel aurait dupliqué la règle et laissé les boutons contredire les avertissements affichés à côté. L'application ne connaît ni la cible ni la source d'un jet : tout ce qui en dépend (critique automatique contre une cible paralysée, sauvegarde contre l'effroi) est un choix explicite du joueur, visible sur le bouton « Jets ».
- **Écarté** : un historique en base (migration, file hors-ligne et endpoint pour le journal d'un seul joueur) ; la détection automatique de la situation (l'application ne l'a pas) ; une relance au choix du joueur (Chanceux ne peut jamais être pire qu'un 1 relancé : on l'applique).
- **Limites assumées** : le critique en cours est celui de la *dernière* attaque (Extra Attack ou sort à plusieurs rayons : la bascule manuelle corrige) ; ce que la fiche ne connaît pas reste un choix du joueur — que l'effet soit visible (Sens du danger), la source de peur, l'ennemi adjacent de l'Attaque sournoise — et les attaques portées contre le barbare qui attaque témérairement ont l'avantage sans que rien ne le calcule ; l'échec automatique (Étourdi, Paralysé…) est signalé au jet, pas appliqué à son résultat ; Chanceux ne vaut pas aux jets contre la mort ; aucune attaque à mains nues n'existe dans l'application (ni bouton, ni calcul), si bien qu'un bonus de dégâts hors arme ne vise que les sorts ; Effrayé désavantage les jets même si la source de peur est hors de vue, que le joueur corrige par « Normal » ; pas d'ordre de tour (la fiche ne connaît pas les autres combattants) ni de journal de session au-delà des jets ([#199](https://github.com/kevmorpain/le-bureau-du-jdr/issues/199)).

### <a id="d23"></a>D23 — Préférences : le premier réglage pose le substrat de D18, les ajustements manuels passent par les effets temporaires
- **Contexte** : désactiver les jets de dés, y saisir son résultat et corriger CA, vitesse, initiative et DD à la main ([#188](https://github.com/kevmorpain/le-bureau-du-jdr/issues/188), [#189](https://github.com/kevmorpain/le-bureau-du-jdr/issues/189), [#191](https://github.com/kevmorpain/le-bureau-du-jdr/issues/191)).
- **Décision** : [D18](#d18) appliquée telle quelle. Migration 0126 : `preferences` JSON nullable sans `DEFAULT` sur `character_sheets` **et** `users`. L'ensemble canonique, son Zod et la résolution `fiche ?? compte ?? défaut codé` sont dans `shared/rules/preferences.ts` ; un réglage de plus est une clé de plus. Le GET de la fiche expose `owner.preferences`, et le client résout avec la fonction partagée (`useCharacterPreferences`) plutôt que de lire une valeur résolue côté serveur, qui serait périmée dès le premier basculement. La page fournit `rollsEnabled` par le moteur de jets (`rollEngineKey`) : tout composant le lit par `useRollsEnabled()`. Éditeur par fiche tri-état (défaut du compte / oui / non) dans l'en-tête ; défauts du compte dans le menu du compte (`/api/account/preferences`).
- **Jets désactivés** : `roll()` ne fait rien et rend 0, et chaque site qui décide d'après le résultat propose une saisie à la place (jet contre la mort : d20 obtenu, table aléatoire : résultat, initiative : total obtenu) ou garde son choix manuel (concentration : Réussi / Raté, recharge d'objet). Les boutons qui portent aussi une information (« Attaque +7 », « Dégâts 1d8+3 ») deviennent des étiquettes (`RollButton`).
- **N4 : pas de table d'ajustements.** Les effets temporaires (migration 0107) donnaient déjà `armor_class_bonus`, `initiative_bonus` et `spell_save_dc_bonus` ; seule la vitesse manquait. `speed_bonus` (mètres fixes, par pas de 1,5) rejoint donc les effets temporaires et alimente `speedBonusParts`. **Écarté** : une surcharge absolue, qui dupliquerait ce patron et resterait fausse dès que l'armure ou la caractéristique change.
- **Limites assumées** : une surcharge *absolue* (« la CA vaut 17 quoi qu'il arrive ») n'existe pas, seulement des bonus nommés ; les dés de vie ne soignent pas d'eux-mêmes (le jet est informatif, le soin se saisit dans les PV), donc n'ont pas de saisie ; les défauts du compte exigent le réseau (pas de file hors-ligne) ; hors fiche (table aléatoire du catalogue), aucune préférence n'est lue et les jets restent actifs.

### <a id="d24"></a>D24 — Fiche de sort : des faits en colonnes, des descriptions en Markdown léger
- **Contexte** : le type d'attaque d'un sort se déduisait de « dégâts sans DD » (faux dans les deux sens, cf. S4 de [`fonctionnalites-manquantes.md`](./fonctionnalites-manquantes.md)), la zone et le coût d'une composante n'existaient que dans la prose, et les descriptions s'affichaient en un bloc ([#167](https://github.com/kevmorpain/le-bureau-du-jdr/issues/167), [#168](https://github.com/kevmorpain/le-bureau-du-jdr/issues/168), [#169](https://github.com/kevmorpain/le-bureau-du-jdr/issues/169), [#170](https://github.com/kevmorpain/le-bureau-du-jdr/issues/170), [#180](https://github.com/kevmorpain/le-bureau-du-jdr/issues/180), [#239](https://github.com/kevmorpain/le-bureau-du-jdr/issues/239)).
- **Décision** : trois colonnes explicites sur `spells` (`attack_type`, `area_of_effect`, `material_cost`), posées par la migration 0127 et par le seed, qui se valident mutuellement (`test/nuxt/spellSheetMigration.test.ts`) ; des tests-contrats (`test/unit/spellSeedData.test.ts`) exigent qu'un sort dont le texte décrit une zone, une attaque de sort ou une composante chiffrée la déclare. Les descriptions passent en Markdown léger (paragraphes, puces, gras, liste numérotée), rendu par `parseMarkdown` en nœuds de texte : ni HTML ni lien, donc rien à assainir sur une colonne que l'éditeur de sort laisse libre.
- **Pourquoi** : une colonne par fait se teste et se migre sans toucher aux autres ; un champ unique `effects` structuré aurait demandé de re-semer tous les sorts. Le Markdown complet aurait imposé une dépendance et un assainissement pour un besoin de trois constructions. Les faits viennent d'AideDD page par page ; la prose AideDD n'est pas reprise.
- **Tables de sort** : un sort renvoie à une table à lancer par `spells.roll_table_id`, comme `features.roll_table_id` (migration 0128, autosuffisante : elle crée la table si le sort existe déjà). La prose des sorts concernés renvoie à « la table ci-dessous » et un test-contrat garde le lien dans les deux sens. Éclair de chaos n'en est pas : son type de dégâts se lit sur l'un des d8 du jet de dégâts.
- **Limites assumées** : les descriptions restent la formulation du seed, qui n'est pas celle d'AideDD (similarité médiane 0,31 sur 116 sorts) : seule leur structure a changé, aucun mot (vérifié). Remplacer ces textes par ceux d'AideDD relève de [#222](https://github.com/kevmorpain/le-bureau-du-jdr/issues/222). La zone est celle du niveau de base ; Espièglerie de nathair et Barbes argentées (hors AideDD) n'ont de faits que d'après le seed.

### <a id="d25"></a>D25 — Inventaire et objets : un seul modèle de dés supplémentaires, des choix du joueur pour la portée, une limite gardée côté fiche
- **Contexte** : `extra_damage` n'avait aucun lecteur et deux formes incompatibles, les manifestations du Pacte de la lame n'étaient lues par rien, la propriété `thrown` ne servait qu'à afficher une portée, l'harmonisation n'était qu'une alerte ([#138](https://github.com/kevmorpain/le-bureau-du-jdr/issues/138), [#139](https://github.com/kevmorpain/le-bureau-du-jdr/issues/139), [#158](https://github.com/kevmorpain/le-bureau-du-jdr/issues/158), [#162](https://github.com/kevmorpain/le-bureau-du-jdr/issues/162), [#165](https://github.com/kevmorpain/le-bureau-du-jdr/issues/165), [#181](https://github.com/kevmorpain/le-bureau-du-jdr/issues/181), [#186](https://github.com/kevmorpain/le-bureau-du-jdr/issues/186)). Les munitions ([#161](https://github.com/kevmorpain/le-bureau-du-jdr/issues/161)) restent ouvertes.
- **Décision** :
  - **Dés supplémentaires.** `extra_damage` quitte l'union. Attaques sauvages devient `critical_extra_dice`, comme Critique brutal (migration 0147) ; les dés de critique de sources différentes s'additionnent, ceux de l'espèce compris (ils n'entrent pas dans les traits de classe). L'éditeur d'objet écrit `weapon_damage_dice` avec `weapons: 'all'` : les dés valent pour l'arme qui les porte, liée si l'objet l'exige, et se jettent à part en Mode Combat.
  - **Arme de pacte.** `shared/rules/pactWeapon.ts` lit `pact_weapon_modifier` et ne l'applique qu'à l'entrée `is_pact_weapon` ; le nombre d'attaques ne se cumule pas avec Attaque supplémentaire (le plus grand l'emporte).
  - **Lancer.** Une arme de corps à corps à lancer garde son attaque de mêlée et gagne un lancer, qui est une attaque à distance : même caractéristique, bonus « à distance » des effets, mais ni Rage, ni Duel, ni dés de critique de mêlée. Une bascule Mêlée / Lancer par arme (mêlée par défaut) n'affiche qu'un jeu de boutons à la fois : deux jeux côte à côte, aux libellés identiques, se lisaient mal. « Longue portée » et « Ennemi à 1,50 m » sont des choix du joueur par arme ([D22](#d22) : l'application ne connaît pas la cible), gardés dans le navigateur comme les états (`useWeaponRange`).
  - **Harmonisation.** La limite de trois objets est gardée par la fiche (`toggleAttuned`, interrupteur grisé), pas par l'endpoint.
  - **Recherche et lentille.** La recherche par nom est un utilitaire partagé (`shared/utils/search.ts`) ; la lentille de sorts lit les objets et effets temporaires du GET par `sheetActiveEffectSources`, aussi lu par le level-up.
- **Pourquoi** : `weapon_damage_dice` existait déjà, typé et rendu en Mode Combat, alors que l'union d'`extra_damage` ne décrivait qu'un seul trait. Un refus serveur ne se rejoue pas : `offlineMutate` ne met pas en file une erreur de réponse et `flushCharacter` s'arrête à la première opération en erreur, donc un 4xx sur l'harmonisation resterait en tête de la file hors-ligne et bloquerait tout ce qui la suit.
- **Écarté** : donner un lecteur à `extra_damage` (ré-implémenter `critical_extra_dice` et `weapon_damage_dice`) ; faire de Lame assoiffée une Attaque supplémentaire de classe (elle vaudrait pour toutes les armes) ; saisir la distance en mètres (rien à calculer sans cible) ; garder la limite d'harmonisation dans l'endpoint ; décompter les munitions (les tables jouent différemment : ce serait un réglage de plus dans `shared/rules/preferences.ts`, [D23](#d23)).
- **Limites assumées** : le cumul d'Attaques sauvages et de Critique brutal est une lecture, AideDD n'en dit rien ; le style Archerie n'est pas appliqué au lancer (règle non vérifiée) ; la portée maximale n'est pas imposée ; les choix de distance survivent à un rechargement, comme les états ; Champion primitif n'est pas appliqué à la création au niveau 20, car `useBuilderSheetProjection` ne projette aucun effet de classe ; une notation d'objet autre que « NdM » reste en `extra_damage`, inerte.

### <a id="d26"></a>D26 — Choix de classe : un chemin générique pour les options de feature, des libellés pour les choix qui ne sont que du texte
- **Contexte** : le Maître de guerre n'avait aucune manœuvre, le Rôdeur aucun ennemi ni terrain, le Champion aucun deuxième style, le builder n'exigeait pas la sous-classe et la fiche de l'Occultiste affichait trois pactes sans dire lequel il avait pris ([#127](https://github.com/kevmorpain/le-bureau-du-jdr/issues/127), [#128](https://github.com/kevmorpain/le-bureau-du-jdr/issues/128), [#172](https://github.com/kevmorpain/le-bureau-du-jdr/issues/172), [#174](https://github.com/kevmorpain/le-bureau-du-jdr/issues/174), [#175](https://github.com/kevmorpain/le-bureau-du-jdr/issues/175)). Les règles viennent des pages AideDD « Guerrier » et « Rôdeur ».
- **Décision** :
  - **Sous-classe.** Le builder l'exige quand le niveau y donne accès ; le serveur reste permissif, comme pour les autres choix (il borne le maximum, jamais le minimum). « Faveur de pacte » devient un `choice_carrier` et le pacte choisi une ligne de la fiche, posée à la création et au level-up, rétro-remplie par la migration 0148.
  - **Libellés du Rôdeur.** `favored_enemy` rejoint `terrain` dans les choix de libellé (migration 0149). Un point de choix qui grandit avec le niveau revient au level-up avec son seul surplus (`choicesGainedAtLevelUp`) ; le serveur refuse de reprendre une valeur déjà choisie ; la fiche les affiche sous la capacité (`labelPicks`).
  - **Options de feature.** `featurePicks` : un point de choix `feature_group` se résout par le catalogue, se valide (`featurePicksError`) et s'enregistre en `character_choices` **et** en `character_features`. Une option déjà portée ne se reprend pas, ce qui force le deuxième style à différer du premier. Un point de choix `replaceable` échange une option déjà prise contre une nouvelle (`featureReplacements`). Il couvre six types : style de combat de la classe, deuxième style du Champion, pacte, manifestations, Métamagie et manœuvres (les quatre premiers sont passés par ce chemin dans un second temps, voir la mise à jour ci-dessous).
  - **Maître de guerre.** Seize manœuvres taguées, de coût un dé ; le compteur de dés suit [D20](#d20) (`superiority_dice`, effet `resource_die`, `meta.cost`) ; le DD de manœuvre prend la meilleure de la Force et de la Dextérité (`saveDcAbility` accepte une liste) ; l'outil de Disciple martial est un choix `tool` porté par la sous-classe (migrations 0150 et 0151).
- **Pourquoi** : le style de combat de la classe, la Métamagie, les manœuvres et le deuxième style auraient été quatre copies du même pipeline (état du builder, champ du payload, sélecteur, étape de level-up, résumé). Le lot a d'abord posé le chemin générique pour les deux types nouveaux et laissé les chemins dédiés (Métamagie, manifestations, pacte, style de classe) en l'état pour borner le risque.
- **Écarté** : copier le pipeline de la Métamagie pour les manœuvres et ajouter un `secondFightingStyle` ; élargir `fighting_style` à plusieurs picks ; migrer dans ce lot les quatre chemins dédiés (la création et le level-up y auraient été réécrits d'un coup) ; exiger la sous-classe côté serveur (une règle de complétude que nul autre choix n'a).
- **Limites assumées** : les fiches déjà créées n'ont aucun choix enregistré (Rôdeur, Champion de niveau 10 ou plus, Maître de guerre) et ne complètent qu'aux paliers suivants ; « deux races d'humanoïdes » est un seul choix, les races ne sont pas enregistrées ; l'avantage contre l'ennemi juré, la maîtrise doublée sur le terrain et la langue de l'ennemi ne sont pas calculés (la fiche ne connaît pas la cible, [D22](#d22)) ; les effets des manœuvres restent en texte, la fiche dépense le dé et le joueur le lance ; l'étape de level-up qui héberge les ennemis jurés s'appelle « Maîtrises » ; le texte seedé d'« Explorateur-né » omet la maîtrise doublée et celui d'« Observation de l'ennemi » dit « une information » là où AideDD parle de deux caractéristiques.

**Mise à jour (2026-10-19) — les chemins dédiés sont migrés.** Le style de combat de la classe, le pacte, les manifestations occultes et la Métamagie passent par `featurePicks` / `featureReplacements`, à la création et au level-up ; `fightingStyle`, `pactBoon`, `invocationIds` / `newInvocationIds` / `replacedInvocationId` et `metamagicIds` / `newMetamagicIds` disparaissent du payload, de l'état du builder et du level-up, et du serveur (`applyInvocationChanges`, `applyMetamagicChanges`, `resolveFightingStylePick`, `resolvePactBoonFeatureId`). Un seul sélecteur (`FeaturePickPicker`) remplace `InvocationPicker` et `MetamagicPicker`.
- **Décisions.**
  - **Remplacement.** Les manifestations se remplacent à chaque niveau de la classe, même quand le niveau n'en donne aucune nouvelle : le point de choix détenu revient du level-up avec `count` 0 (`REPLACEABLE_EVERY_LEVEL_KINDS`). Les manœuvres gardent leur règle (on n'échange qu'en en apprenant de nouvelles) ; la Métamagie 2014 reste non remplaçable (`replaceable: false`).
  - **Prérequis.** Le serveur résout les options sans l'état du personnage (`ignorePrerequisites`) : il vérifie l'appartenance au groupe, le niveau de la classe, le nombre et les doublons, pas le pacte, les sorts ou les caractéristiques exigés, comme avant. L'interface montre le verrou d'une option plutôt que de la masquer (`unmetPrerequisite`).
  - **Doublons entre points de choix.** `featurePicksError` refuse une même option choisie sur deux points de choix de la même requête : le deuxième style diffère du premier même quand les deux arrivent ensemble.
  - **Pacte.** Le pacte se lit dans le nom de l'option choisie ; `character_classes.pact_boon` reste écrit comme projection (comme `subclass_id`), de même que le familier de la Chaîne. `pactWeaponItemId`, `pactWeaponInventoryId` et `pactBoonCantripIds` restent des champs à part : ce ne sont pas des options de feature.
  - **Atomicité.** Au level-up, la manifestation, son sort octroyé et son remplacement s'écrivent dans le lot atomique (`featurePickStmts`), non plus après lui.
  - **Fiches existantes.** La migration 0152 consigne en `character_choices` les options que les fiches portent déjà, sans quoi `replacedPickError` refuserait de remplacer une manifestation existante. Elle ne reprend pas sur le style de la classe celui que le Champion a pris sur son propre point de choix.
- **Plus strict qu'avant** : le level-up borne désormais les manifestations et la Métamagie au surplus que le niveau accorde (l'ancien chemin ne vérifiait que l'appartenance au groupe) et refuse une option déjà portée ; un style de combat envoyé hors de son palier est refusé au lieu d'être ignoré en silence. Le golden-master C2 en tire parti : il remplace une manifestation au niveau 11 au lieu d'en ajouter une que le niveau n'accorde pas.
- **Écarté** : conserver les anciens champs à la frontière de l'API et les convertir côté serveur (quatre contrats pour une seule logique) ; une PR par type (l'état du builder et du level-up aurait été réécrit quatre fois) ; faire valider les prérequis d'état par le serveur (il ne connaît pas les caractéristiques finales à la création ni les sorts de la même requête ; le contrat resterait conservateur).
- **Limites assumées** : les prérequis des manifestations restent à la charge de l'interface ; un point de choix `replaceable` n'a qu'une règle de remplacement par type, fixée dans le code et non dans la donnée ; le serveur ne borne que le maximum de picks, jamais le minimum (on peut en prendre moins que dus) ; retirer une manifestation retire aussi le sort qu'elle octroyait, même si une autre manifestation encore portée l'octroie (comportement conservé) .

### <a id="d27"></a>D27 — Maîtrises de compétence et de jet de sauvegarde : dérivées, plus les ajouts manuels
- **Contexte** : `character_skills` mêlait trois choses, des copies de règles d'avant [D8](#d8) (compétences de classe et d'historique, jets de sauvegarde), des choix (expertise, compétences de multiclassage) et des ajouts manuels ; les jets de sauvegarde y vivaient sous `<carac>_save`, ce qui interdisait la clé étrangère vers `skills` voulue par [D7](#d7) ([#122](https://github.com/kevmorpain/le-bureau-du-jdr/issues/122), [#125](https://github.com/kevmorpain/le-bureau-du-jdr/issues/125)).
- **Décision** :
  - **Ce que les règles accordent se dérive.** Compétences de classe et de multiclassage : choix sur le point « Compétences de classe » de leur classe ; expertise : choix sur le point d'expertise, lu en effet `skill_expertise` (`deriveChoiceProficiencies`) ; historique personnalisé : ses colonnes `skill_proficiencies` / `tool_proficiencies` / `language_proficiencies` (`deriveBackgroundProficiencies`), comme un historique seedé l'est de son porteur.
  - **Le reste est un ajout manuel**, dans la seule table `character_proficiency_overrides`, pour tous les types : armes, armures, outils, langues, et désormais `skill` et `saving_throw` (valeur : la clé de compétence ou de caractéristique), action `grant` / `revoke` / `expertise`. La compétence et la langue de l'Humain variant, que le catalogue ne modélise pas, y sont rangées à la création.
  - **Une règle de lecture** (`shared/rules/proficiencyLevels.ts`) : le niveau le plus haut des effets et des ajouts ; un retrait l'emporte. Le GET de la fiche sert ses `proficiencyOverrides` ; la fiche, l'inventaire et le level-up les lisent là, sans fetch dédié (`useCharacterProficiencyOverrides`).
  - **Migration 0153** : chaque ligne de `character_skills` est rangée là où la fiche la retrouve au même niveau (choix, historique personnalisé, ajout manuel) ou supprimée quand une règle l'accorde déjà ; puis `character_skills` et `skills` disparaissent.
- **Pourquoi** : un nouveau type de maîtrise devient une valeur d'enum, pas une table ; une nouvelle source (objet, don qui donne l'expertise) est un effet ou un choix, sans copie à resynchroniser ; la fiche lit les maîtrises par un seul chemin.
- **Écarté** : séparer les seuls jets de sauvegarde pour poser la clé étrangère (deux tables d'ajouts manuels pour une même règle) ; une contrainte `CHECK` sur la colonne mixte (la table `skills` restait décorative) ; garder `character_skills` pour le seul manuel.
- **Limites assumées** : aucune clé étrangère sur les valeurs des ajouts (polymorphes) : Zod valide chaque écriture (`proficiencyOverrideSchema`) ; une compétence de multiclassage copiée avant ce lot est rattachée à la classe principale quand sa liste la propose ; l'Humain variant reste sans espèce en base ; entre l'application de la migration et le déploiement du Worker, l'ancien Worker lit une table supprimée.

### <a id="d28"></a>D28 — Équipement de départ : des références au catalogue, des sacs dépliés, des munitions décomptées sur réglage
- **Contexte** : l'équipement de départ du builder était du texte (« 2 hachettes », « Arbalète légère + 20 carreaux », « Paquetage du donjon ») joint au catalogue par nom exact ; ce qui ne s'y trouvait pas était journalisé puis jeté, et le reste arrivait à l'inventaire en quantité 1 ([#126](https://github.com/kevmorpain/le-bureau-du-jdr/issues/126), [#207](https://github.com/kevmorpain/le-bureau-du-jdr/issues/207)). Le catalogue n'avait ni sac, ni focaliseur, ni munition ([#161](https://github.com/kevmorpain/le-bureau-du-jdr/issues/161)).
- **Décision** :
  - **Des références, pas des libellés.** `shared/rules/startingEquipment.ts` : un groupe est fixe ou à options ; une option liste des objets du catalogue (nom et quantité), des choix d'objet par sélecteur (catégorie d'arme, type d'outil, catégorie d'équipement : « arme courante », « focaliseur arcanique »…), des sacs et de l'or. Les candidats d'un choix se lisent dans le catalogue, plus dans une liste recopiée (`GENERIC_ITEM_OPTIONS` disparaît). L'origine (`class:fighter`, `background:soldier`) préfixe les choix mémorisés : ils ne survivent pas à un changement de classe.
  - **Les sacs se déplient** (décision du PM sur #207) : le Sac d'explorateur devient sac à dos, sac de couchage, 10 torches, 10 rations… avec leurs quantités, sur la fiche. Rations et torches se décomptent, les munitions aussi.
  - **Le contrat d'écriture porte des ids et des quantités** : `inventory: [{ itemId, quantity }]`. Le serveur refuse un objet inconnu ou retiré (`validateInventory`) ; `inventoryItemNamesUnresolved` disparaît. Un test-contrat garde que chaque objet cité par les classes, les historiques et les sacs existe une seule fois dans le catalogue seedé.
  - **Catalogue** : migration 0154 (`INSERT OR IGNORE`, ids 120 à 194) et seed identiques (un test les compare) ; les 7 armes à munitions reçoivent `ammunition_type` (`UPDATE … json_set` en migration, parce que le seed n'insère que les ids absents).
  - **Munitions** (`shared/rules/ammunition.ts`) : chaque attaque avec une arme à munitions consomme une pile du bon type ; sans munition, l'arme ne tire pas. La moitié se récupère en fin de combat (AideDD) : le joueur rend les munitions à la main. Le décompte est un réglage, `ammunition` (défaut : désactivé, choix du PM : les tables jouent différemment), que [D25](#d25) avait écarté faute de réglage ([D23](#d23)). Désactivé, aucune arme n'est bloquée ni décomptée, comme avant ce lot.
  - **Les listes de départ** des 12 classes et 14 historiques sont recoupées avec AideDD page par page : le Barbare n'avait pas de choix de sac, les sacs portaient des noms inexistants (« Paquetage du donjon » pour « Sac d'exploration souterraine »), l'Enfant des rues recevait un jeton de chance au lieu d'une souris domestiquée.
- **Pourquoi** : la jointure par nom était la cause de la perte, pas un symptôme ; la corriger au catalogue (objets) et au contrat (ids) la rend impossible, là où garder les libellés l'aurait seulement rendue visible.
- **Écarté** : ajouter des clés à `GENERIC_ITEM_OPTIONS` et une table texte des sacs (garde la jointure par nom) ; persister les objets non résolus en objets sur mesure (un « Vêtements communs » par fiche, quantités à 1) ; un sac comme objet unique du catalogue (rien ne s'y décompte) ; décompter les munitions sans réglage (les tables jouent différemment).
- **Limites assumées** : l'équipement perdu avant ce lot n'a jamais été enregistré, il n'y a rien à rattraper ; AideDD ne dit pas quelle munition tire quelle arme, `ammunition_type` se déduit des noms (arc → flèche, arbalète → carreau, fronde → bille, sarbacane → aiguille) ; une arme sur mesure sans `ammunition_type` n'est pas suivie ; un choix d'objet vaut un objet (les 10 bouteilles de l'escroc sont un lot nommé) ; ni poids ni prix ([#153](https://github.com/kevmorpain/le-bureau-du-jdr/issues/153), [#159](https://github.com/kevmorpain/le-bureau-du-jdr/issues/159)) ; deux « Outils de voleur » existent au catalogue (ids 69 et 110), la référence précise `itemType: 'tool'` ; une fiche qui active le réglage sans munitions à l'inventaire ne tire plus.

### <a id="d29"></a>D29 — Poids, prix et encombrement : des entiers au catalogue, la variante sur réglage
- **Contexte** : `items` n'avait ni poids ni prix, la bourse était déclarative et rien ne disait ce qu'un personnage porte ([#153](https://github.com/kevmorpain/le-bureau-du-jdr/issues/153), [#159](https://github.com/kevmorpain/le-bureau-du-jdr/issues/159)).
- **Décision** :
  - **Colonnes** `weight_g` (grammes), `cost_cp` (pièces de cuivre) et `lot_size` sur `items` (migration 0155). `NULL` : la règle n'en donne pas (objets de saveur d'historique, objets magiques) ; `0` : AideDD note « - ». Les valeurs viennent d'un tableau par nom (`server/db/seeds/data/itemPricing.ts`), lu par le seed et recopié dans la migration ; un test les compare. Les objets sur mesure saisissent un poids en kg et un prix en po.
  - **Un lot** porte le poids et le prix de `lot_size` unités : 20 flèches pour 1 po, 20 billes pour 4 pc, donc 37,5 g le carreau, que des entiers par unité ne rendent pas. La fiche somme `quantité × poids / lot`.
  - **Règle partagée** (`shared/rules/encumbrance.ts`, `currency.ts`) : capacité de charge = Force × 7,5 kg, doublée par catégorie de taille au-delà de Moyenne et réduite de moitié pour Très petite ; une pièce pèse 10 g ; monture et véhicule ne se portent pas ; change standard 1 po = 10 pa = 100 pc, 1 pp = 10 po = 20 pe. La fiche affiche le poids porté sur la capacité, et le poids et le prix de chaque ligne.
  - **La variante est un réglage** (`encumbrance`, désactivé par défaut, comme les munitions, [D28](#d28)) : au-delà de 2,5 fois la Force en kg, vitesse -3 m ; au-delà de 5 fois, -6 m et désavantage aux jets de Force, de Dextérité et de Constitution (`RollFacts.heavilyEncumbered`) ; la colonne Force des armures est ignorée (AideDD), donc la pénalité de [R10](./fonctionnalites-manquantes.md) tombe.
- **Pourquoi** : AideDD présente l'encombrement comme une « Variante » ; la capacité de charge, elle, est la règle de base. Le poids se lit toujours, ses effets se choisissent.
- **Écarté** : le poids dans le JSON `properties` (non sommable, absent des objets d'un autre type) ; des kilogrammes décimaux ; la variante toujours active ; un prix par unité arrondi (une bille à 0,2 pc).
- **Limites assumées** : 23 objets d'historique n'ont ni poids ni prix et comptent pour rien ; les objets magiques non plus ; au-delà de la capacité la règle ne prévoit rien de plus, la fiche applique les effets de « fortement encombré » (lecture) ; la taille ne modifie pas les seuils de la variante, seulement la capacité (lecture) ; pousser, tirer et soulever (le double de la capacité) ne s'affichent pas ; aucun effet de type « Puissante carrure » ; les poids 5.5 ne sont pas sourcés.

### <a id="d30"></a>D30 — Effets d'espèce lus : PV du Nain, expertise conditionnelle, sens
- **Contexte** : trois effets déclarés par les seeds n'avaient aucun lecteur ([#235](https://github.com/kevmorpain/le-bureau-du-jdr/issues/235) E13, [#131](https://github.com/kevmorpain/le-bureau-du-jdr/issues/131) E1, [#137](https://github.com/kevmorpain/le-bureau-du-jdr/issues/137) E8).
- **Décision** :
  - **Ténacité naine** : `hp_per_level` +1 dans les deux seeds du Nain des collines (la lignée et l'ancienne espèce, que le test d'équivalence garde identiques) et migration 0156. Le PM n'a qu'une fiche concernée, dont il avait déjà relevé les PV à la main : la migration retranche le niveau total du `hp_base` des fiches existantes (la part « dés » de [D19](#d19)), pour que leur maximum affiché ne change pas. Elle ne joue que tant que le trait n'a pas son effet, donc rejouée elle ne retranche rien de plus ; les fiches créées ensuite ont les bons PV d'emblée.
  - **Expertise conditionnelle** : l'application ne connaît pas le contexte d'un test d'Histoire. `skill_bonus` suit donc les situations de l'avantage conditionnel : le joueur désigne « origines d'un travail de maçonnerie » ou « objets magiques, alchimiques ou technologiques » dans le lanceur de dés, et `conditionalSkillBonus` (`shared/rules/rolls.ts`) ajoute au jet ce qui manque pour atteindre le double du bonus de maîtrise, même sans maîtrise de la compétence (les deux traits le disent). L'expertise a déjà le double, la moitié de Touche-à-tout est remplacée. Le jet note le bonus et la situation est consommée.
  - **Sens** : `shared/rules/senses.ts` lit la vision dans le noir et les `sight_modifier` ; la carte « Perc. passive » en affiche la portée et les liste au survol.
- **Écarté** : un bonus d'expertise appliqué sans désignation (faux hors contexte) ; corriger les PV des fiches existantes à la main (une migration le fait pour toutes) ; prévenir à l'ouverture de la fiche (un état de lecture par fiche pour une seule fiche concernée).
- **Limites assumées** : « Maître des ombres » (`invisible_in_dim_light`) est une capacité activable, listée avec les sens faute d'autre endroit ; les sens spéciaux sans effet seedé (perception des vibrations…) ne sont pas modélisés ; la situation se désigne pour le prochain jet, comme celles de l'avantage.

### <a id="d31"></a>D31 — Le builder projette les capacités de classe
- **Contexte** : le récapitulatif du builder ignorait tout effet de classe ([#298](https://github.com/kevmorpain/le-bureau-du-jdr/issues/298) F20, reste de [#165](https://github.com/kevmorpain/le-bureau-du-jdr/issues/165)). Un Barbare créé au niveau 20 n'avait pas Champion primitif (+4 Force et Constitution, maximum 24), plafonné à 20 par un `Math.min` local ; Touche-à-tout du Barde (niveau 2) et Athlète accompli du Guerrier Champion (niveau 7) manquaient à l'initiative et à la Perception passive.
- **Décision** :
  - **Un canal de catalogue** : `GET /api/catalog/class-features` (`loadClassFeatures`) rend les capacités passives de classe et de sous-classe qui portent des effets, avec leur niveau. La sélection est celle de `createCharacter` (`isPassiveGrant`, type `class_feature` ou `subclass_feature`) ; un test-contrat compare ce que le catalogue annonce à ce que la création attribue. Le front filtre au niveau choisi par `featureEffectsOf`, la garde de niveau de la fiche (`useClassFeatureEffects`).
  - **Les scores passent par la règle de la fiche** : `finalAbilities` additionne les bonus naturels (espèce, ASI, dons, capacités de classe) et les borne par `resolveAbilityScore` ; le maximum est relevé par les `ability_max_increase` de l'espèce, des dons et des capacités (`sumAbilityMaxIncreases`, que `computeAbilityScores` utilise aussi).
  - **Le projecteur reçoit les mêmes effets** (`featureEffects`, sans les `ability_increase` déjà comptés) : initiative, Perception passive, compétences et PV du récapitulatif suivent la fiche. Un total de PV saisi à la main au niveau 20 d'un Barbare se convertit avec la Constitution de la fiche.
- **Écarté** : embarquer les capacités dans `/api/catalog/classes` (lu aussi par le level-up et les sorts, pour un besoin du seul builder) ; faire calculer les scores par le calculateur de la fiche (le projecteur dépend de `useCharacterBuilder`, et `finalAbilities` alimente déjà PV, CA et sorts) ; coder Champion primitif en dur (ne couvre aucune autre capacité).
- **Limites assumées** : la vitesse (`speed_bonus` du Barbare et du Moine, qui dépend de l'armure) et la CA du récapitulatif restent celles de l'espèce et du modificateur de Dextérité ; le plafond de 20 de l'étape d'ASI reste celui de la règle des ASI ; une capacité sans effet seedé n'apparaît pas au catalogue.

### <a id="d32"></a>D32 — Capacités à usages limités : un compteur ou une réserve, et les disciplines des quatre éléments comme des choix
- **Contexte** : 50 capacités de classe, dont sept absentes du relevé de [#231](https://github.com/kevmorpain/le-bureau-du-jdr/issues/231) (cinq de l'Occultiste, Source d'inspiration, Restauration ensorcelée), déclaraient un `rechargeType` sans `maxUsesFormula` ni réserve ([#231](https://github.com/kevmorpain/le-bureau-du-jdr/issues/231) C10, [#232](https://github.com/kevmorpain/le-bureau-du-jdr/issues/232) C11). La fiche n'affichait aucun compteur, le repos remettait à zéro un usage que personne ne comptait, et dépenser une option de Conduit divin d'un domaine ne baissait pas la réserve.
- **Décision** : aucun mécanisme neuf ([D20](#d20)) ; des données seedées, migrées par la 0157 sans reseed.
  - **Compteur** : `maxUsesFormula` + `rechargeType` pour les capacités à usages limités (Illumination protectrice, Sens divin, Coup de chance, Chance du ténébreux…). Les nombres viennent des pages de classe d'AideDD.
  - **Coût** : `meta.cost` pour les 17 options de Conduit divin (Clerc et Paladin, une utilisation chacune) et pour les capacités de ki de sous-classe (Paume frémissante 3, Arts des ombres 2). Les capacités de classe du Moine (Âme de diamant 1, Vide immaculé 4, Projection astrale 8) rejoignent `Ki.meta.spends`, comme Parade de projectiles : `spends` ignore la sous-classe, `cost` non. `ClassResourcesSection` titre la liste des coûts par réserve (Manœuvres, Conduit divin, Capacités de ki).
  - **Pas de recharge sans effet** : `Incantation` (Ensorceleur, Escroc arcanique), `Source d'inspiration`, `Restauration ensorcelée`, `Tranquillité`, `Regard hypnotique` et `Charme instinctif` n'ont plus de `rechargeType`. Leur recharge est portée par un effet (`resource_regain`), une règle de repos automatique ou un verrou par créature, pas par un compteur.
  - **Test-contrat** (`test/unit/featureCounters.test.ts`) : toute capacité qui déclare une recharge porte un compteur ou paie une réserve, et toute capacité qui paie une réserve nomme une réserve que porte une autre capacité.
  - **Disciplines de la Voie des quatre éléments** (migration 0158, `elemental_disciplines.ts`) : seize options taguées `elemental_discipline`, payées en ki par `meta.cost` et jamais attribuées d'office, sur le chemin générique des `featurePicks` ([D26](#d26)) comme les manœuvres. Le point de choix de « Disciple des éléments » donne une discipline au niveau 3 puis une aux niveaux 6, 11 et 17, remplaçable en en apprenant une nouvelle ; Lien élémentaire est acquise d'office et son texte, comme celui du lancer de sort élémentaire (ki supplémentaire, plafond par niveau), reste dans « Disciple des éléments ». Le niveau de moine exigé par une discipline est son `levelRequired` : `resolveChoices` ne propose pas les autres, le serveur les refuse.
  - **Perfection de l'être** : `Ki.meta.regains` (`label`, `amount`, `minClassLevel`, `whenEmpty`), symétrique de `meta.spends` ; la carte de ki propose « Perfection de l'être (+4) », active à réserve vide au niveau 20.
- **Écarté** : une liste d'exceptions dans le test-contrat (retirer la recharge sans effet est plus simple et ne laisse rien à justifier) ; un `meta.cost` à plusieurs coûts pour Désertion de l'âme (`Ki.spends` existe) ; une capacité « Lien élémentaire » séparée (elle exigerait de rattraper les fiches existantes, pour un texte sans coût ni mécanique) ; un effet `resource_regain` déclenché à l'initiative pour Perfection de l'être (il toucherait l'union d'effets et `restRecovery` pour une seule capacité) ; un compteur global pour Regard hypnotique et Charme instinctif (le verrou est par créature).
- **Lectures assumées** : « une fois par jour » (Restauration arcanique) est le repos long ; Sorts de prédilection compte une pastille par sort ; Surcharge magique compte l'usage gratuit ; Présage compte un d20 par pastille (deux, trois au niveau 14) ; Intervention divine compte un usage rendu par le repos long, alors qu'après un succès le blocage dure 7 jours (l'application n'a pas d'horloge de jeu). Sens divin suit AideDD à la lettre (1 + modificateur de Charisme, sans minimum) ; Marée du chaos se recharge à la main quand le MD déclenche un Pic de magie sauvage. Sombre délire passe de repos long à repos court (AideDD). Les disciplines que la page AideDD donne sans ligne de prérequis n'ont pas de prérequis de niveau (lecture de l'absence) ; le jet de sauvegarde de Fouet de l'onde et de Poing de l'air prend le DD de ki, que la page ne cite pas pour elles mais qui est le seul DD de la section.
- **Limites assumées** : les sorts lancés par une discipline ne sont pas reliés au catalogue de sorts (la description nomme le sort) et le ki supplémentaire qui en relève le niveau se dépense à la main avec « Dépenser » ; Perfection de l'être ne se déclenche pas d'elle-même au jet d'initiative (la fiche ne connaît pas l'ordre des tours, [D22](#d22)) : le joueur la déclenche ; les fiches existantes de la Voie des quatre éléments n'ont aucune discipline enregistrée (même limite que [D26](#d26)) ; la réserve de Conduit divin du Paladin reste à 1 utilisation, AideDD ne donnant pas de palier par niveau.

### <a id="d33"></a>D33 — Fin de la Rage : des drapeaux de meta lus par des règles pures, et un joueur qui répond ce que la fiche ignore
- **Contexte** : une rage ne s'arrêtait qu'au repos ou au bouton « Mettre fin », et rien ne signalait qu'un barbare ne lance pas de sorts en rage ([#234](https://github.com/kevmorpain/le-bureau-du-jdr/issues/234) C13). Les règles viennent de la page AideDD « Barbare » : la rage finit si le barbare devient inconscient, ou si son tour se termine sans qu'il ait attaqué une créature hostile ni subi de dégâts depuis son tour précédent ; Rage persistante (niveau 15) ne garde que l'inconscience et l'arrêt volontaire ; il ne peut ni lancer de sorts ni se concentrer pendant la rage.
- **Décision** : quatre drapeaux dans la meta de « Rage » (`endsWhenUnconscious`, `endsWithoutCombat` avec `persistentFromClassLevel: 15`, `blocksSpellcasting`), lus par trois fonctions pures de `shared/rules/classResources.ts` (`endingWhenUnconscious`, `lapsingWithoutCombat`, `spellcastingBlockedBy`), sans règle par classe dans le code, sur le modèle de `endsOnNewTurn` (Attaque téméraire). La migration 0159 pose la meta et le texte sur les bases déployées.
  - **Inconscience** : `useUnconsciousEndings`, monté une fois par la page de la fiche, surveille « à 0 PV ou état Inconscient » et coupe les capacités concernées, quelle que soit la façon d'y arriver (dégâts, PV saisis à la main, état posé à la main). Les dégâts s'appliquent côté client (`HitPointsSection`) : il n'y a rien à brancher côté serveur. Une fiche déjà à 0 PV au chargement n'est pas touchée.
  - **Faute de combat** : au « Nouveau tour » du Mode Combat, une question non bloquante demande si le joueur a attaqué une créature hostile ou subi des dégâts depuis son tour précédent ; « Non » met fin à la rage, « Oui » la garde. Rage persistante supprime la question.
  - **Sorts** : un avertissement dans la section Magie et dans la modale de lancement, pour un personnage qui peut lancer des sorts.
- **Écarté** : ne brancher la fin que sur la saisie de dégâts (les PV édités à la main, l'état Inconscient et les jets contre la mort y échapperaient) ; suivre automatiquement attaques et dégâts (la fiche ne sait pas si une cible est hostile, [D22](#d22)) ; interdire le lancer de sort (le ticket demande un avertissement, et un MD peut trancher autrement).
- **Limites assumées** : Rage implacable peut garder le barbare à 1 PV, alors que la rage s'est déjà arrêtée à 0 PV : la notification offre « Rétablir (sans coût) », que la fiche ne conditionne à rien ; la durée d'une minute n'est pas suivie (pas d'horloge de jeu), la rage dure toujours jusqu'à un repos ou jusqu'à l'une de ces fins ; une concentration en cours quand la rage commence n'est pas coupée (la page ne le dit pas) ; l'épuisement que la Frénésie du berserker inflige à la fin de la rage n'est pas appliqué ; la question revient à chaque « Nouveau tour », seul repère de tour de la fiche.

### <a id="d34"></a>D34 — Faveurs permanentes (manuels, tomes) et ordre d'un score fixé et d'un bonus d'objet
- **Contexte** : les manuels et tomes (effet définitif d'un objet consommé) n'étaient pas modélisés ([#164](https://github.com/kevmorpain/le-bureau-du-jdr/issues/164) O7a), et l'ordre entre un score fixé (Gantelets de puissance d'ogre) et un bonus d'objet (Pierre de Ioun de Force) n'était pas sourcé ([#299](https://github.com/kevmorpain/le-bureau-du-jdr/issues/299) O7c, point 4 de [#165](https://github.com/kevmorpain/le-bureau-du-jdr/issues/165)). Les autres points de #165 étaient déjà livrés : le plafond du builder ([D31](#d31)), la lentille de sorts qui lit les objets (`spellLensItems.test.ts`) et les PV max qui suivent la Constitution des objets (`hitPointsDerivation.test.ts`, [D19](#d19)).
- **Décision** :
  - **Faveurs permanentes** : six features de type `boon` (Manuel de vitalité, Manuel d'exercices physiques, Manuel de vivacité, Traité de perspicacité, Traité d'autorité et d'influence, Traité de compréhension), chacune `ability_increase` +2 et `ability_max_increase` +2 sur sa caractéristique. `featureEffectsOf` les lit comme un don, sans condition de niveau ni de classe ; elles se portent sans objet équipé. Leur type propre les garde hors des choix de dons (ASI, builder, montée de niveau), qui filtrent `feat`. Catalogue `GET /api/catalog/boons` (`loadBoons`), ajout et retrait par les routes `feats` de la fiche (qui acceptent `feat` et `boon`), « Ajouter une faveur » dans la section des capacités (`AddFeatSlideover`, `kind: 'boon'`), étiquette « Faveur ». Le seed des dons sème aussi les faveurs ; la migration 0160, auto-suffisante et tolérante base vierge, les pose sur les bases déployées.
  - **Ordre d'un score fixé et d'un bonus** : `resolveAbilityScore` calcule les deux ordres (bonus puis score fixé, score fixé puis bonus) et retient le plus haut. Force 8 avec Gantelets et Pierre de Ioun de Force (+2, maximum 20) vaut 20 ; l'ancien ordre donnait 19. Pour des bonus positifs, c'est « score fixé puis bonus » ; la fonction ne diffère que pour un bonus négatif, où elle garde le score fixé.
- **Source** : les six livres viennent des pages AideDD de la DMG 2014 (+2 au score et au maximum ; 48 heures d'étude sur 6 jours ou moins ; le livre perd sa magie et la retrouve au bout d'un siècle), lues par un sous-agent. Pour l'ordre : aucun Sage Advice trouvé, aucune des pages AideDD (Gantelets, Pierre de Ioun) ne parle de cumul ; seule une règle de pouce de forum (« l'ordre le plus favorable ») existe, non officielle. C'est un arbitrage, pas une citation.
- **Écarté** : un don `feat` marqué par une catégorie (il apparaîtrait dans les choix d'ASI) ; un consommable qui ajoute la feature à l'usage (plus lourd, et le ticket avait tranché pour des features attachées au personnage) ; garder l'ancien ordre (sans source non plus, et moins favorable) ; inverser sans calculer les deux ordres (un bonus négatif ferait perdre le score fixé).
- **Limites assumées** : la durée d'étude, la perte de magie du livre et son retour au bout d'un siècle ne sont pas suivis ; aucune page ne traite du cumul avec d'autres sources, chaque faveur compte donc pour elle-même (une par caractéristique) ; le catalogue d'objets n'a pas les livres eux-mêmes (D2, [#177](https://github.com/kevmorpain/le-bureau-du-jdr/issues/177)) ; le nom français de la Pierre de Ioun de Force n'est pas sur la page AideDD de la famille.

### <a id="d35"></a>D35 — Sorts du socle : une tranche de niveau par PR, relevée sur les fiches AideDD, posée par migration
- **Contexte** : le seed ne portait que 118 sorts sur environ 360 ([#176](https://github.com/kevmorpain/le-bureau-du-jdr/issues/176) D1) : 16 de niveau 0, 30, 24 et 26 aux niveaux 1 à 3, puis 7, 4, 7 et 4 aux niveaux 4 à 7, aucun aux niveaux 8 et 9. La liste AideDD 2014 (`/dnd-filters/sorts.php`, lue par un sous-agent) donne 220 sorts aux niveaux 4 à 9 : 159 du socle (PHB, SRD, BR+) dont 19 seedés, et 61 hors socle (Xanathar, Tasha) dont 3 seedés.
- **Décision** : des tranches de niveau, une PR chacune, en commençant par le niveau 4 du socle (29 sorts : `spells_niveau_4.ts`, avec ses liens de classes, fusionné par `spells.ts` et `spell_class_mappings.ts`). Les faits viennent de la fiche AideDD de chaque sort (`/dnd/sorts.php?vf=<slug>`, version 2014), lue par des sous-agents qui rendent un JSON compact ; les descriptions sont réécrites en français avec tous les nombres, sans reprendre la prose ([D24](#d24), [#222](https://github.com/kevmorpain/le-bureau-du-jdr/issues/222)). La migration 0161, générée depuis le même seed, pose les sorts et leurs liens de classes sur les bases déployées : auto-suffisante, idempotente, tolérante base vierge (rien n'est posé tant que le catalogue de sorts n'est pas semé), sans reseed manuel contre la limite de requêtes D1. Les tests-contrats de `spellSeedData.test.ts` valident les faits déclarés (zone, attaque, coût de composante, tables de montée en puissance) ; `spellsLevel4Migration.test.ts` compare la migration au seed.
- **Lectures assumées** : les classes que la fiche marque « [TCoE] » (ajouts de Tasha aux listes de classe) ne sont pas liées (Barde pour Assassin imaginaire, Druide et Magicien pour Divination, Rôdeur pour Domination de bête) ; seuls les sorts dont la fiche donne un coût chiffré ou une consommation déclarent `materialCost` (Coffre secret de Léomund : 5 000 po, consommation non dite) ; les dégâts conditionnels qui ne sont pas le jet du lanceur (riposte du Bouclier de feu, dont la fiche ne dit pas quel type va avec quel bouclier, et 4d6 de Porte dimensionnelle en cas d'arrivée occupée) restent dans le texte, sans entrée `damages` ; Mur de feu et Sphère résiliente n'ont pas de `areaOfEffect` (aucune forme du schéma ne convient) ; Fabrication rejoint les plafonds de taille du test (son « cube de 3 mètres » borne un objet).
- **Écarté** : un reseed de prod par `?only=spells` (étape manuelle, limite de requêtes D1) ; mêler les sorts hors socle à la première tranche (ils passent par `source` et le contenu étendu) ; un seul gros lot (relire 140 sorts d'un coup).
- **Limites assumées** : les 29 sorts viennent de sous-agents et n'ont pas été relus un à un contre les fiches ; les niveaux 0 à 3 n'ont pas été comparés à AideDD ; la liste AideDD n'affiche pas les classes, elles viennent de chaque fiche ; les effets chiffrés des sorts actifs ([#245](https://github.com/kevmorpain/le-bureau-du-jdr/issues/245)) restent à faire une fois les sorts en place.
